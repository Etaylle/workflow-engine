| Attribute | Value |
|---|---|

| Obligation level | The keyword in the statement: **MUST** (= shall), **SHOULD**, **MAY** |

## 1. Scope and definitions

**Scope.** This document is the single contract for how a product supports several languages and regional conventions: the locale model, the message catalogue and its syntax, locale-aware formatting, the delivery of translations at runtime through an API (so that a text change does not need a redeployment), the way a client loads and keeps translations for a session, and the translation workflow. It is independent of any product, brand, framework or programming language. The document is self-contained: it states the rules of neighbouring disciplines (API conventions, interface rules, frontend structure) that it needs, so that it can be used with any framework, language and project structure.

| Term | Definition |
|---|---|
| Locale | A language, optionally with script and region, that selects translations and formatting conventions. Identified by a BCP 47 tag (`de`, `de-AT`, `zh-Hant-TW`). |
| Message | One translatable unit of user-facing text, identified by a key, written in a message syntax. |
| Message key | The stable identifier of a message. |
| Catalogue tree | The hierarchy in which all messages of a locale are organised. Its first level holds the domain names and `shared`. |
| Node | An element of the tree: a *branch* (contains nodes) or a *leaf* (one message). A node is never both. |
| Key path | The dot-separated names from the first level to a leaf (`cart.summary.title`). It is the identity of a message. |
| Domain | A bounded area of the product, named as in the architecture (the same name as its domain in the code structure). |
| Namespace | A branch addressed by its path (a first-level node, or a deeper branch) that is loaded as a unit. |
| Source locale | The locale in which messages are originally written. It is complete by definition. |
| Default locale | The locale used when negotiation finds no supported match. |
| Fallback chain | The ordered list of locales consulted when a message is missing in the active locale. |
| Seed catalogue | The source-locale catalogue kept in version control and shipped with the client build. It defines the set of keys and is the last element of every fallback chain. |
| Runtime store | The provider's storage of bundles, which can change without a release. |
| Bundle | The messages of one locale (or the requested namespaces of it) as one tree, in one representation. |
| Locale file | The complete message tree of one locale, as one JSON document without an envelope (the content of `de.json`). It is the unit of every write. |
| Revision | An opaque value that changes whenever the content of a locale file changes. It is carried by the response header `Locale-Revision`. |
| Translation resource | The API resource `/i18n/{locale}` and its operations (section 7). |
| Settings | The status and fallback chain of a locale. They are not part of the locale file. |
| Pseudo-locale | A generated test locale that transforms source text to expose layout, encoding and hard-coded strings. |
| Glossary | The approved terms of the product per locale. |
| Project parameter | A project-specific decision recorded in section 16. |

## 3. Locales and language tags

| ID | Statement | Ver. | Basis |
|---|---|---|---|
| I18N-LOC-001 | A locale MUST be identified by a well-formed BCP 47 language tag. Underscore forms (`de_AT`), ISO 639 codes used as locale identifiers in URIs, and invented codes MUST NOT be used. | T | BCP47 |
| I18N-LOC-002 | Tags MUST be stored and emitted in canonical form (language lowercase, script title case, region uppercase) and MUST be compared case-insensitively. Consumed tags MUST be normalised first. | T | LTLI |
| I18N-LOC-003 | Extension subtags (`-u-`, `-t-`) MUST NOT be part of the identity of a supported locale. Preferences such as calendar, numbering system and hour cycle are user settings passed to formatting, not locales. | I | LTLI |
| I18N-LOC-004 | The supported locales are an explicit list (project parameter P01). Each has a status: `active` (offered and served), `hidden` (served, not offered) or `disabled` (not served). | I | PP |
| I18N-LOC-005 | Exactly one source locale exists (P02). Its seed catalogue is complete and is written first. | I | PP |
| I18N-LOC-006 | A default locale exists (P03, **default** the source locale). It applies only when negotiation finds no supported match. | I | PP |
| I18N-LOC-007 | A bundle is created for a language (`de`) first. A regional variant (`de-AT`) SHOULD contain only the messages that differ and inherit the rest through the fallback chain. | I | PP |
| I18N-LOC-008 | Every locale has a documented, finite, acyclic fallback chain that ends in the source locale (P04). The **default** chain removes subtags from the right and then adds the default locale and the source locale (`de-AT`, `de`, default locale, source locale). Where truncation is linguistically wrong, the chain is written out explicitly. | T | BCP47 |
| I18N-LOC-009 | Negotiation MUST use this order (**default**): the locale in the URL where locale-prefixed URLs are used; the user's saved choice; the `Accept-Language` request header matched by lookup against the supported list; the default locale. | T | PP |
| I18N-LOC-010 | The matching algorithm MUST be stated (lookup, returning one result, with basic language ranges). Quality weights in `Accept-Language` only order the list. | I | LTLI |
| I18N-LOC-011 | A detected locale is a suggestion. A visible language switcher MUST exist, and the user's explicit choice MUST win until they change it. Detection by IP address MUST NOT select a locale, and a redirect by locale MUST always leave a way back. | T | PP |
| I18N-LOC-012 | The saved choice MUST be stored by one documented mechanism (account setting for signed-in users, a functional preference otherwise), consistent with the consent rules of the project. | I | PP |
| I18N-LOC-013 | The `lang` attribute of the document MUST equal the active locale. A passage in another language MUST carry its own `lang` (WCAG 3.1.1, 3.1.2). | T | WCAG |
| I18N-LOC-014 | Public pages that exist in several locales MUST have one URL per locale, a self-referencing canonical link and reciprocal `hreflang` alternates, including `x-default`. The URL form (path prefix **default**, P05) is chosen once. | T | PP |
| I18N-LOC-015 | The set of supported locales MUST be verified at build time against the formatting data of every supported runtime (`supportedLocalesOf` of each `Intl` service). A locale the runtime cannot format MUST NOT be `active`. | T | ECMA402 |
| I18N-LOC-016 | A pseudo-locale (P06, **default** tag `qps-ploc`, from the private-use language range) MUST exist in development and tests, and MUST NOT be served or offered in production. | T | PP |
| I18N-LOC-017 | A locale MUST NOT be activated before its bundle meets the completeness threshold (P07, **default** 100 % of the keys in the seed catalogue, or the fallback chain is accepted for the rest). The provider enforces this when the status changes to `active` (I18N-API-044). | T | PP |
| I18N-LOC-018 | The language switcher MUST list each language by its own name (endonym), with a `lang` attribute per entry, and MUST NOT use flags to represent languages. | I | PP |
| I18N-LOC-019 | A locale value that comes from outside (URL, header, cookie, query, request body, storage) MUST be checked as a well-formed BCP 47 tag and matched against the supported list before it reaches `Intl`, a message formatter or the translation resource. An invalid value is ignored and negotiation continues. | T | BCP47 |
| I18N-LOC-020 | Public pages MUST localise their metadata with their content: title, description, canonical and alternate links, social-preview and structured-data language fields, and the `Content-Language` header. Sitemaps list every locale URL with its alternates. | T | PP |
| I18N-LOC-021 | The URL of the default locale MUST have one canonical form: with the prefix like the other locales, or without it with `x-default` pointing to it. The other form redirects permanently (P05). | T | PP |
| I18N-LOC-022 | The user's time zone is a saved setting (P32). A time zone detected from the browser is a suggestion that the user can change, and is never used as a locale. | T | PP |
| I18N-LOC-023 | Locale-dependent assets (fonts, locale data of third-party components, validation message tables, locale variants of images) MUST be declared per locale and loaded with the bundle. A locale MUST NOT be `active` while one is missing. | T | PP |
| I18N-LOC-024 | A locale change made elsewhere (another device, the account settings) MUST NOT swap the language of a running session without notice. It applies at the next session or after confirmation. | T | PP |

## 4. Messages

### 4.1 Hierarchy of the catalogue

All messages of a locale form one tree. The first level holds the **domain names** and `shared`. The second and third levels follow the project's own **component and semantic hierarchy**. The last segment is the message name.

| Level | Meaning | Examples |
|---|---|---|
| 1 | A domain, or `shared` | `cart`, `account`, `shared` |
| 2 | The first semantic division of the domain: a feature, flow or page; in `shared`, a cross-cutting group or the shared UI | `summary`, `checkout`, `action`, `ui` |
| 3 | A component, pattern or element group inside that division | `itemList`, `form`, `datePicker` |
| 4 to 5 | A part, state or variant, only where it is needed | `email`, `error` |
| Last | The message name, which states the purpose of the text | `title`, `label`, `hint` |

Example tree (non-normative):

```text
shared
  action          save, cancel, delete
  status          pending, done
  validation      required, tooLong
  error           CASE_001 (title, action)
  ui
    datePicker    label, hint, previousMonth, nextMonth
cart
  summary         title, items (plural), empty
  checkout
    form
      email       label, hint, error.invalid
```

| Message name | Use (default vocabulary) |
|---|---|
| `title`, `heading` | The title of a page, dialog, card or section |
| `label`, `hint`, `placeholder`, `help` | Field and control text |
| `description` | Explanatory text |
| `empty`, `loading`, `success`, `warning`, `info` | State text |
| `error.<reason>` | Error text by reason (a branch) |
| `confirm.<part>` | A confirmation dialog (a branch: `title`, `body`, `accept`, `cancel`) |
| `tooltip`, `ariaLabel` | Supplementary and accessible text |
| `action.<verb>` | A button or link text (a branch) |

| ID | Statement | Ver. | Basis |
|---|---|---|---|
| I18N-HIE-001 | The catalogue MUST be one tree. The first level MUST contain only the declared domain names (P29) and `shared`. | T | PP |
| I18N-HIE-002 | A domain name MUST be the name of that domain in the product architecture and the code structure, written in lowerCamelCase, declared once, and stable. `shared` is reserved for text used by more than one domain and corresponds to the shared layer of the code. | I | PP |
| I18N-HIE-003 | The second and third levels MUST mirror the project's component and semantic hierarchy: the features, flows, pages, patterns and components of that domain, named as the architecture and the design system name them. The reference hierarchy is recorded (P30). | I | PP |
| I18N-HIE-004 | Levels four and five MAY be used for parts, states and variants. The depth MUST NOT exceed six levels including the message name (**default**, P13). | T | PP |
| I18N-HIE-005 | The last segment is the message name and states the purpose of the text. The vocabulary of 4.1 applies, and a project MAY extend it. | I | PP |
| I18N-HIE-006 | A node is either a branch or a leaf, never both. `cart.summary` MUST NOT be a message when `cart.summary.title` exists. | T | PP |
| I18N-HIE-007 | Every key path MUST have at least three segments: a first-level node, at least one semantic group, and the message name. | T | PP |
| I18N-HIE-008 | Node names MUST be lowerCamelCase (`[a-z][a-zA-Z0-9]*`). The only exception is a node named by an API error code under `shared.error` (I18N-MSG-025). | T | PP |
| I18N-HIE-009 | A domain's messages MUST live in its own subtree. Code of one domain MUST NOT use a key from another domain's subtree. Text that several domains need lives under `shared`. | T | PP |
| I18N-HIE-010 | `shared` is structured like the shared layer: shared UI components appear as `shared.ui.<componentName>` (the design-system component name in lowerCamelCase), and cross-cutting text appears in groups such as `shared.action`, `shared.status`, `shared.validation` and `shared.error`. A project MAY add groups. | I | PP |
| I18N-HIE-011 | When a second domain needs a message, the message is promoted to `shared` as a new key and the old key is retired (I18N-RTD-006). Cross-domain use of the old key is not a substitute. | I | PP |
| I18N-HIE-012 | The messages of a component live in the node of that component, and each node on levels one to three has one owner and a description in the catalogue metadata. Moving or renaming a component is a rename of its subtree: new keys, with the old ones retired (I18N-MSG-003). | I | PP |
| I18N-HIE-013 | Nodes follow meaning. A node MUST NOT encode layout position, styling, counters, wording, language or locale. Catch-all nodes (`misc`, `other`, `general`, `texts`, `common`) MUST NOT be used. | I | PP |
| I18N-HIE-014 | A branch has at most 200 children (**default**, P13). A larger branch is split by meaning. | T | PP |
| I18N-HIE-015 | The seed catalogue is stored as the same tree, with one file per first-level node, nested identically, with members sorted by code point. Descriptions and other metadata are stored beside the leaves, and branch metadata (owner, description) on levels one to three. | I | PP |
| I18N-HIE-016 | A catalogue map (the tree down to level three with owner and message count) MUST be generated and published with the component gallery. The pipeline fails when a node on levels one to three has no owner or description. | T | PP |
| I18N-HIE-017 | The tree structure is identical in every locale. A locale MAY have a subset of the leaves, but a path that is a leaf in the source locale MUST NOT be a branch in another locale, and the reverse. | T | PP |
| I18N-HIE-018 | The key path (dotted) and the nested form are two spellings of one identity, and tools MUST convert between them without loss. A dot cannot occur inside a node name. | T | PP |
| I18N-HIE-019 | Bundles and exports MUST list the members sorted by code point at every level, so that exports and diffs are stable. | T | PP |
| I18N-HIE-020 | A first-level node is the default unit of loading. A deeper branch MAY be the unit for a large domain. Each route or feature declares the branches it needs (I18N-CLI-006). | I | PP |
| I18N-HIE-021 | A message used by several components of one domain lives in the lowest common branch of those components and is not duplicated. | I | PP |
| I18N-HIE-022 | A component that several domains use lives under `shared.ui`. A domain-specific wrapper keeps only its own text in its domain subtree. | I | PP |
| I18N-HIE-023 | Plural, ordinal and gender variants of one message live inside that message (one leaf), never as separate keys (`items.one`, `items.other`). | T | PP |
| I18N-HIE-024 | Technical names (class names, route names, file names) MUST NOT be node names unless they are the project's published component or semantic names (I18N-HIE-003). | I | PP |

### 4.2 Message rules

| ID | Statement | Ver. | Basis |
|---|---|---|---|
| I18N-MSG-001 | A message key is the key path of its leaf in the hierarchy (4.1), with at least three and at most six dot-separated segments, at most 128 characters (**default** pattern `^[a-z][a-zA-Z0-9]*(\.[a-zA-Z0-9_]+){2,5}$`), for example `checkout.summary.title`. | T | PP |
| I18N-MSG-002 | A key describes purpose and place, never the wording. Changing the source wording MUST NOT change the key. | I | PP |
| I18N-MSG-003 | A key MUST NOT be reused for a different meaning. Renaming is a new key plus the removal of the old one. | I | PP |
| I18N-MSG-004 | The first segment of a key is its first-level node: a domain or `shared`. The `shared` branch is loaded at start. Other branches are loaded when the feature that uses them is needed (section 8). | I | PP |
| I18N-MSG-005 | One message syntax MUST be used in the whole project (P08, **default** ICU MessageFormat). Unicode MessageFormat 2 MAY be chosen when every library that parses messages (client and provider) supports it. The syntax is a project decision and MUST NOT be dictated by the frontend framework or by a library's private dialect. A library MAY be used only if it implements the chosen syntax, with all CLDR plural categories and named arguments. | I | MF |
| I18N-MSG-006 | The provider MUST be able to parse the chosen syntax, so it can validate messages on write (I18N-API-014). If it cannot, the syntax is restricted to a subset it can validate, and the subset is documented. | T | PP |
| I18N-MSG-007 | A message is a complete sentence or unit. Sentences MUST NOT be built by concatenating messages or fragments, and a sentence MUST NOT be split across keys, because word order differs by language. | T | PP |
| I18N-MSG-008 | Arguments MUST be named (`{count}`, `{userName}`), never positional. Argument names are descriptive lowerCamelCase. | T | PP |
| I18N-MSG-009 | A translation MUST NOT use an argument the source message does not define, and MUST use every argument the source defines at least once. The check applies to the message as a whole, so a plural branch MAY omit the count where the language reads naturally. | T | PP |
| I18N-MSG-010 | Plurals MUST use the plural construct with the CLDR categories of the target language (`zero`, `one`, `two`, `few`, `many`, `other`). `other` is mandatory. Every category the language requires MUST be present. A category the language does not use MUST NOT be present. | T | CLDR |
| I18N-MSG-011 | Exact-value branches (`=0`) MAY be used for special wording and do not replace the required categories. Code MUST NOT select a message by comparing the count itself. | T | MF |
| I18N-MSG-012 | Ordinals use the ordinal construct, never the cardinal plural construct. | T | CLDR |
| I18N-MSG-013 | Grammatical variants (gender, case, role) use the select construct with a mandatory `other` branch. The selector comes from a closed set, not free text. Wording SHOULD be neutral where the language allows it. | T | MF |
| I18N-MSG-014 | Numbers, dates, times, currencies and lists inside a message MUST be formatted by the message syntax's formatters or the shared formatting utility, with the active locale. Code MUST NOT pass pre-formatted values. | T | ECMA402 |
| I18N-MSG-015 | Messages MUST NOT contain HTML. Emphasis and links use tag placeholders (`<b>…</b>`, `<link>…</link>`) from a closed list (P09, **default** `b`, `i`, `link`) that the renderer turns into elements. A URL MUST NOT be written in a message; it is an argument supplied by code. | T | PP |
| I18N-MSG-016 | A message MUST be rendered as text. `innerHTML` and equivalents MUST NOT be used for messages, and every argument MUST be treated as text. | T | PP |
| I18N-MSG-017 | The seed catalogue stores, for each message, a description for translators (what it is, where it appears, what each argument is, with an example value), an optional maximum length, and a status. A description is required where the message has an argument or an ambiguous word. | I | PP |
| I18N-MSG-018 | The same source word with different meanings MUST use different keys (verb "Open" and state "Open"). | I | PP |
| I18N-MSG-019 | A message MUST respect the maximum length for its kind of element (P31, **default** table in 13.2), and the layout MUST tolerate text at least 40 % longer than the source text. A per-message maximum is checked in the pipeline against the seed metadata. | T | PP |
| I18N-MSG-020 | The glossary (P10) lists approved terms per locale. Brand and product names that must not be translated are arguments or carry `translate="no"`. Glossary terms are enforced by lint where possible. | I | PP |
| I18N-MSG-021 | A message value MUST NOT be the empty string. An intentionally absent text omits the element. An empty value means *missing*. | T | PP |
| I18N-MSG-022 | Values of unknown direction (names, titles, free text) inserted into a message MUST be isolated (`<bdi>` or `dir="auto"` on their element). | T | PP |
| I18N-MSG-023 | Translated messages MUST NOT be case-changed by CSS `text-transform`. Where capitals are required they come from the message or from a locale-aware method with the locale given. | T | CLDR |
| I18N-MSG-024 | Accessible names and descriptions, alternative text, page titles, validation messages, live-region announcements and tooltips are messages and follow this document. | T | WCAG |
| I18N-MSG-025 | A problem from the API is shown through a message selected by its error code, never by the provider's human-readable text, which is content only. The key path is `shared.error.<CODE>` with the message names `title` and optionally `action` (`shared.error.CASE_001.title`). A domain MAY refine a code in its own subtree (`<domain>.<group>.error.<CODE>.title`), and the shared message is the fallback. | T | PP |
| I18N-MSG-026 | A message MUST NOT contain personal data, secrets or environment-specific values. These are arguments. | T | PP |
| I18N-MSG-027 | Punctuation, quotation marks and ellipses are those of the locale and are part of the translation. Code MUST NOT add punctuation around a message. | I | PP |
| I18N-MSG-028 | A message value MUST NOT begin or end with whitespace, and MUST NOT contain control characters other than a line feed, or bidirectional override and embedding characters (U+202A to U+202E). Spacing belongs to the layout. | T | PP |
| I18N-MSG-029 | User-supplied text MUST NEVER be used as a message pattern or be concatenated into one. It is only ever an argument and is shown literally, including braces, tag-like text and message-syntax characters. | T | PP |
| I18N-MSG-030 | A value from data (status, category, role) MUST be displayed through a message selected by the neutral value. An unknown value MUST show a neutral message (`shared.status.unknown`) and MUST NOT show the raw code. Values travel as neutral codes and are never localised in transport. | T | PP |
| I18N-MSG-031 | Logs, metrics labels, analytics event names, API codes, enumeration values, field names in transport and file names MUST NOT be localised. They stay in one neutral language. | I | PP |
| I18N-MSG-032 | An argument MUST NOT be a translated noun, verb or phrase inserted into a sentence, because gender, case and agreement differ by language. The sentence is written whole per case, or a `select` on a neutral code chooses between whole sentences. | T | PP |
| I18N-MSG-033 | Gender and other personal attributes used in a `select` come from data the user provided, never from inference. Absent data selects the neutral `other` branch. | T | PP |

## 5. Formatting and locale conventions

| ID | Statement | Ver. | Basis |
|---|---|---|---|
| I18N-FMT-001 | Dates, times, numbers, currencies, units, lists, relative times and display names MUST be formatted through one shared utility based on `Intl`, with the locale as an input. Manual string building of these values MUST NOT be used. | T | ECMA402 |
| I18N-FMT-002 | Interchange values are locale-neutral: RFC 3339 instants, `YYYY-MM-DD` calendar dates, JSON numbers or decimal strings, ISO 4217 currency codes with the amount, explicit units, E.164 phone numbers. APIs MUST NOT return formatted display strings. | T | LTLI |
| I18N-FMT-003 | An instant is displayed in the user's time zone (setting) or the documented project zone, passed explicitly as `timeZone`. A calendar date (birthday, due date) MUST NOT be shifted by a time zone. | T | PP |
| I18N-FMT-004 | Date and time output uses style options (`dateStyle`, `timeStyle`) rather than hand-written patterns. A custom pattern needs a documented reason. | I | ECMA402 |
| I18N-FMT-005 | Separators, grouping and digits come from the locale. A decimal or grouping character MUST NOT be hard-coded. | T | ECMA402 |

## 6. Runtime delivery of translations

Translations are content that changes more often than code. The design has three layers: the **seed catalogue** shipped in the build (the floor that always works), the **runtime store** behind the translation resource (the editable system of record), and the **session cache** in the client (memory plus session storage).

| Order | Source consulted for a message in locale L | Notes |
|---|---|---|
| 1 | Runtime bundle of L, from the session cache | Loaded from the translation resource. |
| 2 | Runtime bundle of each locale in the fallback chain of L, in order | Loaded with L (I18N-CLI-012). |
| 3 | Seed catalogue of the source locale | Always present in the build. |

| ID | Statement | Ver. | Basis |
|---|---|---|---|

Delivery options considered (non-normative): translations compiled into the build (needs a redeployment for every text change); static files served from a CDN and fetched by the client; a managed translation platform that publishes to a CDN; the project's own API. This document's default is delivery through the project's own API because it gives validation on write, one access model and no extra service; a project MAY choose a CDN or platform by parameter P18, and the client rules in section 8 and the message rules in section 4 still apply. All options are consumed by plain HTTP requests, so none requires a particular framework.

## 7. The translation resource

All paths are under the versioned API base (`/api/v1`). `{locale}` is a BCP 47 tag in lowercase (`de`, `de-at`, `zh-hant-tw`).

**Principle.** A locale is changed only by sending its **complete locale file**. Whoever adds a text, changes a text, removes a text or adds a language reads the current file, changes it locally and sends the whole file with `POST /i18n/{locale}`. The stored file is always replaced as a whole. Partial updates of the file are not provided. An optional single-message write exists as a convenience (I18N-API-057); the server applies it to the stored file, and the result is the same as uploading the whole changed file.

| Operation ID | Method and path | Purpose | Success | Notable errors |
|---|---|---|---|---|
| `listLocales` | `GET /i18n` | List the locales with settings and size | 200, 304 | |
| `getLocaleFile` | `GET /i18n/{locale}` | Read the complete locale file, optionally limited by `namespace` | 200, 304 | 404 `I18N_010` |
| `getLocaleFileHeaders` | `HEAD /i18n/{locale}` | Read the headers (`ETag`, `Locale-Revision`) only | 200 | 404 `I18N_010` |
| `uploadLocaleFile` | `POST /i18n/{locale}` | Send the complete locale file: creates the locale, or replaces its whole file | 201, 200 | 400, 412 `I18N_013`, 413, 415, 422, 428 `I18N_014`, 409 `I18N_015` |
| `deleteLocale` | `DELETE /i18n/{locale}` | Remove the locale and its file | 204 | 404, 409 `I18N_009`, 412, 428 |
| `getLocaleSettings` | `GET /i18n/{locale}/settings` | Read status and fallback chain | 200, 304 | 404 |
| `replaceLocaleSettings` | `PUT /i18n/{locale}/settings` | Replace status and fallback chain | 200 | 404, 409 `I18N_009`, 412, 422, 428 |
| `getLocaleMessage` | `GET /i18n/{locale}/messages/{keyPath}` | Read one message (optional, P37) | 200, 304 | 404 `I18N_019` |
| `putLocaleMessage` | `PUT /i18n/{locale}/messages/{keyPath}` | Add or replace one message (optional, P37) | 201, 200 | 404, 412, 422, 428 |
| `getLocaleCoverage` | `GET /i18n/{locale}/coverage` | Counts of translated and missing keys (optional, P20) | 200 | 404 |
| `listLocaleMissingKeys` | `GET /i18n/{locale}/missing-keys` | Keys of the source locale not yet translated (optional, P20) | 200 | 404 |

Response headers of the file operations (non-normative summary of I18N-API-007, I18N-API-063):

| Header | Meaning |
|---|---|
| `ETag` | Strong validator of the returned representation. |
| `Locale-Revision` | Opaque value of the file state. Identical for every read of the same file state, also for filtered reads. Compared for equality only. |
| `Last-Modified` | Time of the last change of the file. Used to ignore older responses. |
| `Content-Language` | The locale of the file. |
| `Cache-Control`, `Vary` | Explicit cache lifetime, and `Accept-Encoding`. |

### 14.1 Review gate

A change MUST be rejected when any of these is true.

| ID | Rejection criterion | Ver. |
|---|---|---|
| I18N-REV-001 | Text for people appears outside the catalogue, or a message is built by concatenation, positional arguments or runtime keys (I18N-CON-001, I18N-MSG-007, I18N-RTD-003). | T |
| I18N-REV-002 | A key is used that is not in the seed catalogue, a message lacks a description where one is required, or a key was reused for another meaning (I18N-RTD-002, I18N-MSG-003, I18N-MSG-017). | T |
| I18N-REV-003 | Dates, numbers, currencies, lists, sorting or case are handled without the shared `Intl` utility and the active locale (section 5). | T |

| I18N-REV-013 | The provider's write checks are incomplete: strict bodies, the activation check, protected locales, limits, `405` with `Allow` (I18N-API-042 to I18N-API-065). | T |

| I18N-REV-016 | A pipeline gate of 14.7 is missing or failing. | T |
| I18N-REV-017 | A locale change is made in any way other than uploading the complete file, or the single-message write is used for bulk changes (I18N-API-050, I18N-API-057). | T |

### 14.2 Definition of done

A change is done only when:

- Every text it adds or changes is a message with a key, a source text and a description, placed in the right node of the hierarchy, and the key check passes.
- Placeholders, plural categories and markup validate for every locale the change touches.
- The change works in the source locale, in the pseudo-locale, in a layout check that uses logical properties, and in each `active` locale.
- Formatting uses the shared `Intl` utility, and tests fix the locale and time zone.
- Changes to the translation resource are in the contract first, with examples and every error code, and the contract test passes.
- The seed catalogue and the runtime store are consistent, and the drift report is reviewed.
- Tools and pipelines that change a locale read the current file and upload the complete file with `If-Match`; none sends a partial file.
- Texts follow the translatability rules: whole sentences, no translated fragments as arguments, data values shown through messages, neutral technical names.
- For a new or changed locale: metadata, fonts and third-party locale data, market-specific content, and the activation check are in place.
- The pipeline gates of 14.7 pass.
- No deferred item was implemented.

### 14.3 Agent workflow for a message change

1. Read the requirement and the glossary. If the wording is a product decision, ask the user (I18N-CON-011).
2. Find the node in the hierarchy: the domain (or `shared` if more than one domain needs it), then the component and semantic path of the project. Add or change the message in the seed catalogue with key, source text and description. Use a new key for a changed meaning.
3. Use the key in code through the localisation layer. Pass named arguments and neutral values.
4. Run the key check, the argument and plural checks, and the pseudo-locale and long-text checks.
5. Check formatting in the shared utility, with the locale and time zone fixed in tests.
6. Confirm the release order (I18N-WFL-003) and the drift report.
7. Check the review gate (14.1) and the definition of done (14.2).

### 14.4 Agent workflow for a new locale

1. Confirm the locale in the supported list (P01) and the fallback chain (P04). Do not invent either (I18N-CON-011).
2. Check that the runtime supports its formatting data (I18N-LOC-015) and that the fonts cover its script (I18N-CNT-014).
3. Create it by uploading its complete file with `POST` (the locale becomes `hidden` with the default fallback chain), then set the fallback chain with `PUT .../settings`.
4. For every later change, read the current file, change it locally and upload the whole file with `If-Match`. Fix every violation reported.
5. Run the linguistic check and the layout check of every template in that locale.
6. Verify the completeness threshold, then set the status to `active` with `PUT .../settings`.
7. Record the result in the release notes (I18N-WFL-012).

### 14.5 Acceptance criteria

```gherkin
Feature: Runtime translations

  Scenario: A text changes without a deployment
    Given the locale "de" is active and a client has loaded its file
    When a permitted caller reads the file, changes "shared.action.save" locally and uploads the complete file with POST and the current ETag
    Then the response is 200 with a new ETag and Locale-Revision
    And a new session shows the new text without a new build
    And a running session shows it after its next revalidation

  Scenario: A partial file is not accepted as a change
    When a caller uploads only the changed keys of "de" with POST
    Then the other messages would be removed
    And the response is 422 with code I18N_018 when the removal exceeds the threshold

  Scenario: A new locale is added with its complete file
    When a permitted caller uploads the complete file for "de-at" with POST and no If-Match
    Then the response is 201 with Location
    And the locale has the status "hidden" and the default fallback chain

  Scenario: A single message is added or changed
    Given the single-message operations are enabled
    When a permitted caller sends PUT /i18n/de/messages/shared.status.pending with a text
    Then the response is 200 or 201
    And the file has a new ETag and Locale-Revision
    And the result equals uploading the whole changed file

  Scenario: A client keeps translations for the session
    Given a client has loaded the "shared" namespace of "de"
    When the user reloads the page in the same session
    Then the bundle comes from session storage and is revalidated with If-None-Match
    And a 304 keeps the stored entry

  Scenario: The translation resource is down
    Given the active locale is not the source locale and the resource does not answer
    Then the page renders with the fallback chain and the seed text within the blocking budget
    And fallback passages carry the language attribute of their locale
    And no key is shown as text

  Scenario: An invalid translation is rejected completely
    When an upload contains a missing plural category and a forbidden tag
    Then the response is 422 listing both violations with pointers
    And nothing is stored

  Scenario: Concurrent edits do not overwrite each other
    Given two translators hold the same ETag
    When both upload a file
    Then one succeeds and the other receives 412 and must read the file again

  Scenario: The catalogue keeps its hierarchy
    When an upload contains "cart.summary" as a message and "cart.summary.title" as a message
    Then the response is 422 with code I18N_012
    And nothing is stored

  Scenario: A first-level node must be a domain or shared
    When an upload adds a message under the first-level node "misc"
    Then the response is 422 and nothing is stored

  Scenario: A locale in use cannot be deleted
    Given "de" is the fallback of "de-at"
    When a permitted caller deletes "de" with the current ETag
    Then the response is 409 with code I18N_009
```
